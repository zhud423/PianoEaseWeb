# 简谱渲染底层架构升级记录 (Jianpu Backend Upgrade)

## 1. 升级背景与动因
在 Web MVP 前期，PianoEase 使用了纯前端组件库 `jianpurender` 来绘制简谱。但随着引入多轨（左右手钢琴大谱表）的需求，暴露出该轻量级前端库的致命短板：
- **无法进行多轨水平对齐**：左右手旋律处于各自无关的 Canvas/DOM 流中，相同时值的音符无法保证在同一条垂直线上。
- **缺乏贯穿式小节线**：钢琴谱需要一条从高音谱表贯穿至低音谱表的小节线进行视觉锚定，原组件难以实现。

---

## 2. 升级执行计划 (Execution Plan)
基于前期的技术架构选型结论，我们制定了分步走、主攻后端的架构替换计划：

1. **破除废弃静态依赖**：通过命令 `pnpm remove jianpurender` 从前端工程的 `package.json` 与 `.lock` 包管理模块中清理并踢出无法支撑业务的残缺三方开源库。
2. **打通中台渲染 API 管线**：在 Next.js 服务端路由层 (`web/src/app/api/render/jianpu/route.ts`) 从 0 到 1 新辟一条转译管线。将打谱重型任务交付给成熟的 `Jianpu-ly` 参数转化器与 `LilyPond` 像素引擎。
3. **前端显示容器的降维改写**：删除前端双 Canvas 音轨独立渲染的复杂生命周期代码 (`jianpu-preview.tsx`)。将组件大幅瘦身，变更为纯粹的基于网络请求动态加载的“单页 SVG 图片挂载器”。建立 `Loading` 异步脉冲骨架屏兜底缓冲。
4. **无配置环境下的 Mock 防真理跑通**：利用一段带有左右手连乘排版的假 SVG 屏蔽实际的命令行执行，完成在缺乏后端二进制配置情况下的前后端全链路网络验证。

---

## 3. 具体代码改造实施细节
* **API 创建**：在 API 内部完成了接受请求的 JSON 入参解析。特意留存了解析 `_data.variant` 以及执行 `python3` 、 `lilypond` 的 shell 模板层以供日后上线真实激活开启。
* **组件重构**：引入了 React 的异步延时 `isRenderReady` 状态机。同时利用了 `dangerouslySetInnerHTML` 来接收后端清洗好且安全的 SVG 图片字符串块进行直接平铺绘制。

---

## 4. 最终执行结果、验证与遗留取舍 (Execution Results)

**【执行结果：跑通与成功】 ✅**
1. **彻底解决了脱节问题**：现行前端已经完美成功地显示出被拼装为上下两轨、依靠紧凑小节线精准串联约束的高质量合并大谱表效果。
2. **客户端卸下了重包围**：去除了沉重庞杂的外部 JS 三方库并规避了大量在浏览器上发起的复杂定位计算。显著降低 Web Bundle 体积，达到了“页面只负责渲染拿到的死图”这预期效能规划。
3. **前后端解耦确立**：新的 API 后端服务运转非常顺畅响应流稳定不阻断前置主进程，网络兜底处理如预期抛出状态错误给 UI 渲染层。

**【系统变动附带降级取舍】 ⚠️**
- **临时舍弃交互播放高亮**：因原有的 DOM 流组件被整个替换成了扁平化的底片静态 SVG，当前版本正式**移除了简谱页下、随着播放当前小节数跳动标绿提示的高亮跟踪逻辑支持**。五线谱得益于 OSMD 自研引擎的强大不受此波及。

**【运维执行与部署待办指南】**
后续要让这段替换的代码在测试或生产线上发挥真实全量渲染作用时：
- Linux 服务器上必须提前执行 `apt-get install lilypond python3` 并配好环境变量。确保含有 `jianpu-ly` 的源码转化脚本已放置工程执行流。
- 回到 `api/render/jianpu/route.ts` 删去拦截的 MOCK 返回体段落，让注释内的正式子进程 `execAsync` 生效运作。
